The key things to understand about this Docker setup
Why two Dockerfiles for the server? Your API and your BullMQ workers share the same TypeScript codebase but have different entrypoints. Dockerfile starts src/index.ts (Express). Dockerfile.worker starts src/workers/index.ts (BullMQ). Keeping them separate means you can scale workers independently — if the email queue is backed up, you spin up more worker-email containers without touching the API containers.
Why multi-stage Dockerfiles? Stage 1 installs all dependencies and compiles TypeScript. Stage 2 copies only the compiled JS and production node_modules. Your final image has no TypeScript compiler, no dev dependencies, no source maps — typically 60–70% smaller than a naive single-stage build.
Why docker-compose.dev.yml separately? Development needs volume mounts for hot reload (ts-node-dev watching your source files). Production should never mount source code — it bakes it into the image. The override file pattern lets you have one clean production compose file and layer dev-specific changes on top.
The depends_on + health check combination is critical — your API container should not start until Redis is actually ready (not just the container started). Without health checks, depends_on only waits for the container to start, not for Redis to accept connections. Your workers especially need this since they require Redis from the first millisecond.
CI/CD on Day 28 — the GitHub Actions file does: tsc --noEmit (type check), docker build (both images), push to GitHub Container Registry, SSH into your server, pull new images, docker compose up -d. That's a complete automated deploy triggered by every push to main.
